# 02-L04 GC Used vs Reserved

## 목표
매니지드 힙의 "쓰는 양(GC Used)"과 "OS에서 받아 둔 양(GC Reserved)"이 할당·해제·수집에 따라 어떻게 따로 움직이는지 Development 플레이어에서 확인한다.

## 예측
- 질문: `byte[50MB]` 하나를 (1) 할당한 직후, (2) 참조를 끊고 `GC.Collect()`한 직후, (3) 그 뒤 10초 동안 아무것도 안 했을 때 — GC Used와 GC Reserved는 각각 어떻게 변하는가?
- 학습자 답 (실행 전, 원문 그대로):
  ```
  (1) GC Used +50MB (GC Reserved는 부족한 경우 증가)
  (2) GC Used 감소, Reserved는 그대로
  (3) 그대로
  ```
  (실행 전에 한 번 고친 답. 처음 답은 "(2) 그대로 / (3) GC Used 감소, Reserved는 그대로"였고 학습자가 바로 정정함)

## 실습 구성
- 코드: `UsedVsReservedLab.cs` — 단계마다 5프레임을 넘긴 뒤 Used/Reserved를 세 경로(`ProfilerRecorder`, `Profiler.GetMonoUsed/HeapSizeLong`, `GC.GetTotalMemory`)로 기록. 비교용으로 (4) 같은 크기 재할당, (5) 다시 해제 + Collect 단계도 둔다
- 실행: 에디터 메뉴 `Labs/02/L04 Used vs Reserved` 또는 플레이어 `-lab 02-L04`

## 해석
- 예측과 비교: (1)·(2)·(3) 모두 맞음.
  - (1) Used +50 MB, Reserved 1.34 → 51.84 MB (기존 빈 공간이 부족해서 힙을 키움).
  - (2) 참조를 끊기만 해서는 Used가 그대로다(2a). 매니지드 힙은 참조 카운팅이 아니라 **추적(tracing) GC**라서, 다음 수집이 돌아야 비로소 "안 쓰는 것"으로 판정된다. `Collect` 후(2b) Used만 내려가고 Reserved는 51.84 MB 유지.
  - (3) 10초 동안, 그리고 이후 수집 2번을 더 거쳐도 Reserved는 줄지 않았다. (단, 아래 추가 측정 1에서 IL2CPP는 수집을 더 반복하면 반납함을 확인)
- 한 단계 더:
  - **Reserved는 최고 수위(high-water mark)로 남는다.** 로딩 중 한 번 생긴 일시적 할당 피크가 세션 끝까지 프로세스 메모리로 남는다. 메모리 예산이 빠듯한 모바일·콘솔에서 이게 문제가 된다. 대처는 피크 자체를 줄이는 것 — 큰 임시 버퍼를 재사용하거나(`ArrayPool`), 네이티브 메모리(`NativeArray`)로 옮겨 명시적으로 해제한다.
  - **남은 공간은 재사용된다.** (4)에서 같은 크기를 다시 할당해도 Reserved가 늘지 않았다. 다만 이번에는 연속된 50 MB 빈 블록이 그대로 있었기 때문이다. Boehm은 객체를 옮기지 않는(non-moving, non-compacting) GC라서, 빈 공간이 잘게 쪼개져 있으면(단편화, fragmentation) 합계가 충분해도 큰 배열이 안 들어가 힙이 더 커질 수 있다 (확인 필요, 실측 가능).
  - **큰 할당은 GC를 부른다.** (1)과 (4)에서 `new byte[50MB]` 직후 GC 횟수가 1씩 늘었다. 이 할당 자체가 수집을 유발한 것으로 보인다(정확한 트리거 조건은 확인 필요).
- 추가 측정 1 — 수집을 반복하면 반납되는가 (학습자 요청, 2026-11-01):
  - **백엔드에 따라 다르다.** IL2CPP는 빈 50 MB 블록이 비어 있는 채로 수집을 누적 6~12회 거치자 Reserved가 51.84 → 1.18 MB(= Used)로 내려갔다. Mono는 32회 수집 + 30초 대기 후에도 51.84 MB 그대로.
  - 해석: Boehm GC의 unmap 기능(빈 힙 블록이 정해진 횟수의 수집 동안 계속 비어 있으면 OS에 반납, 기본 임계값 6회로 알려짐)이 IL2CPP의 libil2cpp에는 켜져 있고, 이 Mono 런타임에는 꺼져 있거나 카운터에 반영되지 않는 것으로 보인다. 임계값과 빌드 옵션은 확인 필요. 프로세스의 실제 커밋 메모리(작업 관리자 등)로 OS 반납까지 확인하지는 않았다.
  - 그래서 02-L04 본 측정의 "(3) 줄지 않음"은 **수집이 2회뿐이어서** 나온 결과이고, IL2CPP에서는 "충분히 오래 비어 있으면 줄어든다"가 정확하다.
- 추가 측정 2 — 단편화 (`-fragmentation`, 깨끗한 힙에서 별도 실행):
  - **큰 구멍 단편화 (F)**: 512 KB 블록 100개 중 하나 걸러 해제하면 빈 공간은 25 MB인데, 20 MB 배열을 할당하자 Reserved가 +20.5 MB 늘었다(두 백엔드 공통). Boehm은 객체를 옮기지 않으므로 512 KB 구멍들을 합쳐 20 MB 연속 공간을 만들 수 없다. 전부 해제한 뒤(F4·F5)에는 구멍이 합쳐져 같은 20 MB가 기존 공간에 들어갔다.
  - **희소 생존자 (S)**: 32 B 배열 80만 개 중 64개마다 하나만 남기고 수집해도 Used가 약 56 MB로 남았다(살아 있는 건 원소 약 1.2만 개 + 참조 배열 6.4 MB 정도). 작은 객체는 같은 크기끼리 힙 블록(4 KB 단위로 알려짐)에 모여 있는데, 블록마다 생존자가 하나씩 남아 블록 전체가 "사용 중"으로 남는다. IL2CPP에서는 이어서 20 MB를 할당하자 Reserved가 +20.5 MB 늘었다. Mono는 F 단계에서 남은 빈 큰 블록에 들어가 늘지 않았다 (실행 순서 때문에 S 단계 대조가 깨끗하지 않음).
  - Used가 "살아 있는 바이트"가 아니라 "사용 중인 블록" 기준이라는 점은 이 결과와 맞지만, Boehm의 지연 스윕(lazy sweep)이 섞였을 가능성도 있다 — 남은 블록의 빈 칸이 같은 크기 할당에 재사용되는지 재보면 가를 수 있다 (확인 필요).
  - 실무 함의: 오래 사는 객체와 짧게 사는 객체를 같은 시기에 섞어 할당하면, 짧은 것이 죽은 뒤에도 오래 사는 것들이 블록을 붙잡아 공간이 재사용되기 어렵다. 장수 객체는 초기화 때 몰아서 할당하고, 큰 버퍼는 재사용한다.
